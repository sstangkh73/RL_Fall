# เป้าหมาย

โปรเจกต์ RL Fall: หุ่นมนุษย์ 3 มิติ (ร่างกาย v1.0, MuJoCo + PPO) ที่เรียนว่าเมื่อโดนผลักควรกู้หรือควรล้ม
และถ้าต้องล้ม ควรล้มแบบไหน
path ทั้งหมดในไฟล์นี้นับจาก root ของโปรเจกต์ (`C:\RL_Fall`) แผนละเอียดอยู่ใน `planning/Curriculum_Plan_TH.md`

## คำถามวิจัย (ระยะยาว)

1. **ควรกู้หรือควรล้ม (S2):** หุ่นรู้ได้ไหมว่าแรงผลักครั้งนี้กู้ได้หรือไม่ ถ้ากู้ได้ให้ยืนต่อ
   ถ้ากู้ไม่ได้ให้ยอมล้มแบบปลอดภัย เพราะการฝืนกู้แล้วพลาดมักเจ็บกว่าการล้มอย่างตั้งใจ
2. **เลือกอวัยวะรับแรง (S3):** อวัยวะมีลำดับความสำคัญ (ศีรษะ > ลำตัว > แขน/ขา)
   ถ้าอวัยวะที่สำคัญน้อยกว่าเล็กน้อยเป็นสิ่งที่ภารกิจถัดไปต้องใช้
   หุ่นเลือกเอาอวัยวะอื่นรับแรงแทนได้ไหม

## เป้าหมายรอบนี้ (ระยะสั้น)

มีผลมากพอและน่าเชื่อถือพอที่จะใช้ **ขอโควตา LANTA** และ **คุยกับอาจารย์ที่ปรึกษา**
คือมีหลักฐานว่าโจทย์นี้เรียนรู้ได้จริง มีคำตอบเบื้องต้นของคำถามที่ 1
และประเมินได้ว่าต้องใช้ compute เท่าไหร่สำหรับงานเต็ม

ทุกผลต้องรันด้วย 3 seeds และรายงานทุก seed รวมถึง seed ที่ไม่ผ่าน ห้ามเลือกเฉพาะ seed ที่ดี

## Milestones

### M1 — ผ่าน gate S1 (ยืนสบาย รอดด้วยการตอบสนอง)

สถานะ 7 ต.ค.: ก้าวตอบสนองผ่าน 3/3 seeds แต่ท่ายืนสบายผ่าน 2/3
seed 63002 เท้าเลื่อน 29.8 ซม. ก่อนโดนผลัก เพราะบทลงโทษรวมถูกจำกัดไว้ที่ 1.0 ต่อ step
พอเลื่อนเกิน ~18 ซม. บทลงโทษก็ไม่เพิ่มอีก

- แก้บทลงโทษท่ายืนใน `src/rl_fall/env3d.py` ให้การกางขาเกินขอบมีต้นทุนเพิ่มไปเรื่อยๆ โดย reward ยังไม่ติดลบ
- เพิ่ม test ใน `tests/` ที่พิสูจน์ว่าบทลงโทษเพิ่มขึ้นตามระยะเท้าเลื่อนที่เกิน 8 ซม. และ reward ยังไม่ติดลบ
- เทรนใหม่ 3 seeds (63001–63003) ด้วย `scripts/run_stage1_v1_recipe.sh`

**ผ่านเมื่อ** ทุก seed ใน `results/stage1_v1_0/` ได้ผลดังนี้:
- เท้าเลื่อนก่อนโดนผลักไม่เกิน 8 ซม.
- CoM ลดลงไม่เกิน 3 ซม. และลำตัวเอียงไม่เกิน 10°
- อัตรารอดเฉลี่ย 3 seeds ที่ impulse 0.10 ไม่ต่ำกว่า 60%
- สัดส่วนผู้รอดที่ก้าวเท้าเพิ่มขึ้นตามแรงผลัก

### M2 — S2 นำร่อง: ควรกู้หรือควรล้ม

- ใช้ damage แบบถ่วงน้ำหนัก (ศีรษะ 5, ลำตัว 2, แขนและขา 1)
- ไม่จบ episode เมื่อล้ม แต่รันต่อ 2–3 วินาทีหลังลงพื้น
- สุ่มแรงผลักทั้งแบบกู้ได้และกู้ไม่ได้อย่างละครึ่ง โดยใช้เส้นแบ่งจาก M1
- fine-tune จาก policy ของ M1
- เทียบกับ 2 baseline: (ก) ล้มแบบปล่อยตัว (ข) policy ของ S1

**ผ่านเมื่อ** ทั้ง 3 seeds ได้ผลดังนี้ (gate S2 ในแผนข้อ 5):
- อัตรารอดบนแรงผลักที่กู้ได้ไม่ต่ำกว่า policy S1 อย่างมีนัย
- damage ถ่วงน้ำหนักบนแรงผลักที่กู้ไม่ได้ต่ำกว่าทั้งสอง baseline
- false give-up (S1 กู้ได้แต่ S2 ล้ม) ไม่เกิน 10%
- รายงานสัดส่วน damage ที่ศีรษะด้วย

### M3 — ประเมิน compute สำหรับ LANTA

- ใช้ transitions ที่ต้องใช้จนผ่าน gate ของ M1 และ M2 คูณจำนวน seeds และ config ที่งานเต็มต้องใช้
  (ablation, λ sweep ของ S3) แล้วหารด้วย throughput ต่อ node และคูณ buffer 1.3 (แผนข้อ 7)
- มี Slurm job script ที่รัน recipe เดียวกันบน CPU node ได้

### M4 — รายงานสรุปสำหรับอาจารย์และคำขอ LANTA

ไฟล์ `planning/Evidence_Summary_TH.md` ยาวไม่เกิน ~4 หน้า มีเนื้อหาดังนี้:
- คำถามวิจัย
- ผล M1 และ M2 เป็นตาราง 3 seeds พร้อม baseline
- วิดีโอหรือภาพท่าทางที่ใช้ยืนยันว่าไม่มี reward hacking
- ข้อจำกัด: damage เป็น engineering proxy
- แผน S3
- node-hours ที่ขอ

## เสร็จเมื่อ

ผ่าน M1–M4 ครบ และตัวเลขทุกตัวใน `planning/Evidence_Summary_TH.md` ตรงกับไฟล์ผลใน `results/`
งาน S3 (คำถามที่ 2) อยู่นอกขอบเขตรอบนี้ ให้มีแค่แผนกับการ calibrate เบื้องต้น

## สัญญาไฟล์ผล (สิ่งที่ `verify.ps1` ตรวจ)

`verify.ps1` รัน pytest ของโปรเจกต์ใน WSL แล้วตามด้วย `auto-loop/tools/check_goal.py` ซึ่งเขียนสรุปผลไว้ที่
`auto-loop/reports/goal-status.md` path ของ run และ eval ทั้งหมดนับจาก `~/RL_Fall` ใน WSL

- **M1** `auto-loop/milestones/m1_runs.json`
  ```json
  {"seeds": {"63001": "results/stage1_v1_0/seed_63001/<stage>/3d_..._20261009T120000", "63002": "...", "63003": "..."}}
  ```
  แต่ละ run ต้องมี `survival_curve.json` ที่ได้จาก `scripts/stage1_survival.py` และต้องประเมินที่ impulse 0.08, 0.10 และ 0.12
  ชื่อ run ต้องมี timestamp ตั้งแต่ 2026-10-08 ขึ้นไป (เทรนหลังแก้บทลงโทษ)
  ตัวตรวจใช้ `update_N` และ `stance_N` ที่ N สูงสุด
  - เกณฑ์: `feet_drift_m` ≤ 0.08, `com_drop_m` ≤ 0.03, `trunk_lean_deg` ≤ 10 ทุก seed
  - เกณฑ์: survival ที่ 0.10 เฉลี่ย 3 seeds ≥ 60%
  - เกณฑ์: step_rate ที่ 0.12 มากกว่าที่ 0.08 ทุก seed
- **M2** `auto-loop/milestones/m2_summary.json`
  ```json
  {"seeds": {"63001": {"run_dir": "...", "eval_file": "results/stage2/.../s2_eval.json"}, "63002": {...}, "63003": {...}}}
  ```
  `eval_file` ต้องเป็นผลที่สคริปต์ประเมินเขียนออกมา ไม่ใช่เขียนเอง และมี field ดังนี้:
  ```json
  {"script": "scripts/<สคริปต์ที่สร้างไฟล์นี้>.py",
   "recoverable":   {"n_episodes": 48, "s2_survival": 0.9, "s1_survival": 0.92},
   "unrecoverable": {"n_episodes": 48, "s2_weighted_damage": 1.2, "s1_weighted_damage": 2.0, "passive_weighted_damage": 2.5},
   "false_give_up": 0.05, "head_damage_share": 0.1}
  ```
  - เกณฑ์: อย่างน้อย 48 episodes ต่อกลุ่ม
  - เกณฑ์: S2 รอดบนแรงผลักที่กู้ได้ ≥ S1 − 5 จุดเปอร์เซ็นต์
  - เกณฑ์: damage ของ S2 บนแรงผลักที่กู้ไม่ได้ < S1 และ < passive
  - เกณฑ์: false give-up ≤ 10%
- **M3** `planning/LANTA_Compute_Estimate_TH.md` และ `auto-loop/milestones/m3_compute.json`
  ```json
  {"node_hours": 1234, "transitions_to_gate": {"S1": 0, "S2": 0}, "throughput_per_node": 0, "runs": 0,
   "sbatch": ["scripts/lanta/<ชื่อ>.sbatch"]}
  ```
  sbatch ทุกไฟล์ต้องมีอยู่จริงและมี `#SBATCH`
- **M4** `planning/Evidence_Summary_TH.md` ยาวไม่เกิน 16,000 ตัวอักษร ต้องมีเลข seed ทั้ง 3, ค่า node_hours จาก M3,
  คำว่า "S3" (แผน) และ "proxy" (ข้อจำกัดเรื่อง damage)
