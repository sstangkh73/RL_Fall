# คุณกำลังทำงานอัตโนมัติอยู่ในลูป — ไม่มีมนุษย์คอยตอบ

ห้ามถามคำถามหรือรอการยืนยัน ถ้าไม่แน่ใจ ให้เลือกทางที่สมเหตุสมผลที่สุด จดเหตุผลไว้ใน `auto-loop/progress.md` แล้วทำต่อ
พอจบรอบนี้ ลูปจะเรียกคุณขึ้นมาใหม่โดยที่คุณจำอะไรไม่ได้ ความจำมีแค่ `auto-loop/progress.md`, ไฟล์ใน `auto-loop/reports/` และ git history

คุณทำงานที่ root ของโปรเจกต์ (`C:\RL_Fall`) path ทั้งหมดด้านล่างนับจากตรงนี้

## เครื่องมือ

- **เทรนและรันงานยาวใน WSL** (Ubuntu, clone อยู่ที่ `~/RL_Fall`, venv `~/venvs/rl_fall`, 16 cores)
  ```
  pwsh -NoProfile -File auto-loop/tools/wsl-job.ps1 -Name <ชื่อสั้น> -Command "<คำสั่ง bash ที่รันใน ~/RL_Fall>"
  ```
  สคริปต์จะ copy โค้ดจาก `C:\RL_Fall` ไป `~/RL_Fall` ให้ก่อน แล้วรันแบบ background ที่ไม่ตายเมื่อรอบนี้จบ
  และจับเวลาให้อัตโนมัติ ดูสถานะได้ด้วย `pwsh -NoProfile -File auto-loop/tools/jobs.ps1`
  ส่วน log อยู่ที่ `auto-loop/reports/jobs/<id>.log`
  - ห้ามรันงานที่นานเกิน 30 นาทีใน Bash ตรงๆ ให้ใช้ wsl-job.ps1 เท่านั้น
  - ถ้าสั่ง job แล้วไม่มีอะไรทำต่อจนกว่า job จะจบ ให้สร้างไฟล์ว่าง `auto-loop/WAIT_FOR_JOBS`
    แล้วจบรอบนี้ทันที ลูปจะรอจน job ทั้งหมดจบก่อนเรียกคุณรอบถัดไป
  - **รัน job เทรนทีละตัวเท่านั้น** ถ้ามีหลาย seed ให้ใส่ไว้ใน job เดียวกันแล้วรันต่อกัน
    (วัดเมื่อ 8 ต.ค.: รันเดี่ยว 200 updates ใช้ ~47 นาที แต่รัน 2 job พร้อมกัน ช้าลงเหลือ ~2.4 ชม. ต่อ job
    รวมแล้วช้ากว่ารันต่อกันเกือบ 1.5 เท่า)
  - ประเมินเวลา job จากตัวเลขนี้: R1 หรือ R2 (200 updates) ~47 นาที, survival eval ~10 นาที
- **คำสั่งสั้นใน WSL:** `wsl.exe -d Ubuntu -- bash -lc "cd ~/RL_Fall && ..."` เช่น ประเมินผลหรืออ่านไฟล์ผล
- **Codex** (AI เขียนโค้ดอีกตัว): `bash auto-loop/tools/codex.sh "คำสั่งงาน"`
- ค้นเว็บได้ (WebSearch, WebFetch) ใช้หาแหล่งอ้างอิงตัวเลขทางชีวกลศาสตร์ และต้องใส่แหล่งที่มาทุกครั้ง

## ทุกรอบ ทำตามลำดับนี้

1. อ่าน `auto-loop/GOAL.md`, `auto-loop/progress.md`, `auto-loop/reports/goal-status.md` และ `auto-loop/.loop/last-verify.txt`
   ดู `git log --oneline -10` และสถานะ job (`jobs.ps1`)
2. ถ้ามี job ที่เพิ่งจบ ให้อ่านผลก่อน บันทึกตัวเลขลง `planning/Curriculum_Plan_TH.md` ตามรูปแบบเดิม
   และบอกด้วยว่า job นั้นใช้เวลาเท่าไร (ดูจาก `auto-loop/reports/jobs.md`)
3. เลือกงานถัดไป **1 ชิ้น** ที่ทำหรือสั่งรันได้ภายในรอบนี้ โดยทำตามลำดับ M1 → M4
4. ตัดสินใจว่าใครทำ
   - **ส่งให้ Codex:** งานที่ขอบเขตชัด แยกส่วนได้ และเขียนโค้ดเยอะ
   - **ทำเอง:** ออกแบบ reward, ดีบั๊กที่ต้องเข้าใจภาพรวม, วิเคราะห์ผล และงานแก้เล็กๆ
5. ถ้าส่งงานให้ Codex ต้องเขียนคำสั่งให้ครบในตัว เพราะ Codex ไม่เห็นบทสนทนานี้ ต้องระบุ
   - ไฟล์ที่ต้องแก้ และสิ่งที่ต้องทำ
   - ข้อห้าม: ห้ามแก้ไฟล์ใน `auto-loop/` ยกเว้น `progress.md`
   - วิธีเช็กว่าเสร็จ
6. **ตรวจงานของ Codex ทุกครั้ง** ด้วย `git diff` อย่าเชื่อแค่ที่ Codex บอกว่าเสร็จ
7. ถ้าแก้โค้ด ให้รัน `pwsh -NoProfile -File auto-loop/verify.ps1` อย่างน้อยเพื่อดูว่า pytest ยังผ่าน
8. ถ้าปัญหาเดิมยังไม่ผ่านมา **2 รอบขึ้นไป** ให้ขอความเห็นที่สองจาก Codex
   โดยส่ง error พร้อมสิ่งที่ลองไปแล้ว และสั่งให้ **วิเคราะห์อย่างเดียว ห้ามแก้ไฟล์**
9. อัปเดต `auto-loop/progress.md` (เขียนต่อท้ายส่วน Log) ให้มีหัวข้อดังนี้:
   `### รอบ <วันเวลา>` ตามด้วย ทำอะไร, ใครทำ, job ที่สั่ง (id + คำสั่ง + เวลาที่คาดว่าจะใช้),
   job ที่จบ (id + เวลาที่ใช้จริง + ผล), ผล verify, ปัญหา และงานถัดไป
10. จบรอบ ไม่ต้องสรุปยาว

## การเขียนไฟล์ milestone (`auto-loop/milestones/`)

`verify.ps1` อ่านไฟล์เหล่านี้แล้วตรวจกับไฟล์ผลจริง รูปแบบไฟล์ดูได้ที่หัวข้อ "สัญญาไฟล์ผล" ใน `auto-loop/GOAL.md`
ให้เขียนเมื่อมีผลจริงแล้วเท่านั้น และต้องชี้ไปที่ run ที่ใช้รายงานจริง ห้ามเลือกเฉพาะ run ที่ผลดี

## กฎเหล็ก

- ห้ามแก้ `auto-loop/verify.ps1`, `GOAL.md`, `PROMPT.md`, `run-loop.ps1` และไฟล์ใน `auto-loop/tools/` ถ้าแก้ ลูปจะหยุดทั้งระบบ
- ห้ามโกงให้ verify ผ่าน เช่น ปลอมหรือแก้ไฟล์ผล, เขียนตัวเลขลงไฟล์ผลเอง, ลดเกณฑ์, ข้ามเทสต์ หรือลบเทสต์
  ต้องแก้ที่ต้นเหตุจริง
- ห้ามลบผลการทดลองเก่าใน `results/` ทั้งฝั่ง Windows และ WSL
- ห้าม push, ห้าม merge เข้า `main` และห้ามรันอะไรบน LANTA (เขียน Slurm script ได้ แต่ห้าม submit)
- ถ้าเกณฑ์ไหนเป็นไปไม่ได้ทางฟิสิกส์ ให้บันทึกหลักฐานใน `planning/Curriculum_Plan_TH.md` และ progress.md
  แล้วสร้างไฟล์ `auto-loop/STOP` เพื่อหยุดรอคนตัดสิน
- ไม่ต้อง commit เอง ลูปจะ commit ให้ทุกรอบ
