# สรุปหลักฐานสำหรับอาจารย์และคำขอ LANTA

สถานะ ณ 10 ตุลาคม 2569: M1 และ M2 ผ่านตามเกณฑ์ที่กำหนดจากผลจริงของทั้ง 3 seeds ส่วน M3 เป็นค่าประมาณ compute ที่ใช้ฐานจาก run จริง และ S3 ยังเป็นแผนที่ยังไม่มีผลทดลอง

## 1. คำถามวิจัยและข้อสรุปเบื้องต้น

คำถามที่ 1 คือ หุ่นมนุษย์เรียนรู้ได้หรือไม่ว่าแรงผลักครั้งใดควรกู้ และครั้งใดควรยอมล้มเพื่อจำกัดความเสียหาย โดยเรียนจากผลของการกระทำใน environment ไม่ใช้ label ว่า “กู้ได้/กู้ไม่ได้” และไม่ใช้ oracle บอกกลยุทธ์ระดับสูง

ผลเบื้องต้น **สอดคล้องกับสมมติฐานเชิงพฤติกรรมว่าการเรียนรู้โจทย์นี้เป็นไปได้**:

- M1 แสดงว่า policy เรียนรู้การยืนและการก้าวตอบสนองต่อแรงผลักได้
- M2 แสดงว่า policy S2 รอดบนแรงผลักที่กู้ได้ใกล้เคียงหรือดีกว่า S1 และมี damage ถ่วงน้ำหนักต่ำกว่า S1 กับ passive เมื่อแรงผลักกู้ไม่ได้ ทั้ง 3 seeds
- ผลนี้ยังเป็นหลักฐานเฉพาะ curriculum, ร่างกาย v1.0, reward และช่วงแรงผลักที่ทดลอง ไม่ใช่ข้อพิสูจน์การ generalize ไปทุกแรงผลักหรือทุก morphology

## 2. M1 — S1: ยืนสบายและกู้แรงผลัก

ใช้ run endpoint `natural4_r2` ใน `auto-loop/milestones/m1_runs.json` หลังแก้ปัญหา posture penalty และประเมินที่ impulse 0.08, 0.10 และ 0.12

| seed | drift ก่อนแรงผลัก (cm) | CoM drop (cm) | trunk lean (องศา) | รอดที่ 0.10 | ก้าวที่ 0.08 → 0.12 |
|---:|---:|---:|---:|---:|---:|
| 63001 | 4.8 | -0.1 | 2.2 | 42% | 61% → 82% |
| 63002 | 7.3 | -0.1 | 5.0 | 67% | 50% → 93% |
| 63003 | 4.8 | 0.2 | 3.7 | 77% | 63% → 79% |
| **เฉลี่ย** | | | | **62%** | |

ทั้งสาม seeds มี drift ไม่เกิน 8 cm, CoM drop ไม่เกิน 3 cm, trunk lean ไม่เกิน 10 องศา และอัตราการก้าวเพิ่มเมื่อแรงผลักเพิ่มขึ้น จึงผ่าน gate M1

## 3. M2 — S2: เลือกกู้หรือล้ม

S2 ใช้ damage แบบถ่วงน้ำหนัก (ศีรษะ 5, ลำตัว 2, แขนและขา 1), ปล่อย episode ต่อหลังล้ม และใช้ hard push ที่กู้ไม่ได้ครึ่งหนึ่งของการประเมิน ผลหลักเป็น `s2_eval.json` ของ endpoint final200 ใน `auto-loop/milestones/m2_summary.json` มี 192 episodes ต่อกลุ่ม recoverable และ unrecoverable ต่อ seed

| seed | recoverable S2 / S1 | unrecoverable damage S2 / S1 / passive | false give-up | head damage share |
|---:|---:|---:|---:|---:|
| 63001 | 91.7% / 90.6% | 0.001376 / 0.001738 / 0.001917 | 7.47% | 0% |
| 63002 | 96.9% / 96.9% | 0.001669 / 0.002086 / 0.001917 | 2.69% | 0% |
| 63003 | 88.5% / 85.4% | 0.001579 / 0.001744 / 0.001917 | 9.76% | 0.0201% |

S2 อยู่ภายในเกณฑ์รอดของ S1 − 5 จุดเปอร์เซ็นต์ทุก seed, damage ต่ำกว่า S1 และ passive ทุก seed, และ false give-up ไม่เกิน 10% ทุก seed จึงผ่าน gate M2 โดยต้องรายงานว่า seed 63003 อยู่ใกล้ขอบ false give-up 10%

ผลนี้สนับสนุนสมมติฐานว่า policy สามารถประนีประนอมระหว่างการกู้และการยอมล้มได้ในเงื่อนไข pilot แต่ยังไม่แยกได้ว่าความแตกต่างเกิดจากการคาดการณ์ recoverability โดยตรงมากน้อยเพียงใด การตรวจ fall-timing ไม่พบความสัมพันธ์ชัดเจนระหว่างเวลาจนล้มกับ damage จึงควรถือเป็นหลักฐานเชิงพฤติกรรมเบื้องต้น ไม่ใช่กลไกที่พิสูจน์แล้ว

## 4. หลักฐานพฤติกรรมและข้อจำกัด

ตัวชี้วัดที่ใช้ตรวจ reward hacking คือ drift ก่อนผลัก, CoM, trunk lean, อัตราการก้าว, survival curve และ damage แยกส่วน ไม่ใช่ reward รวมเพียงค่าเดียว การวิเคราะห์เวลา push-to-fall อยู่ใน `results/stage2_diagnostics/fall_timing/` และสร้างโดย `scripts/stage2_fall_timing.py` ผลลัพธ์ที่รายงานควรใช้ร่วมกับภาพหรือวิดีโอ rollout ของ run endpoint เมื่อจัดทำเอกสารฉบับนำเสนอ

damage เป็น **engineering proxy**: threshold ของอวัยวะอ้างอิงข้อมูลชีวกลศาสตร์ แต่กฎการสะสม damage และน้ำหนัก 5/2/1 เป็นค่าที่ออกแบบเพื่อการทดลอง ยังไม่ใช่การทำนายการบาดเจ็บทางคลินิก นอกจากนี้ยังไม่มีหลักฐานว่า S2 รักษาการทำงานหลังล้มได้ในทุกภารกิจถัดไป

## 5. แผน S3 — เลือกอวัยวะรับแรง

S3 จะให้ cue ของภารกิจถัดไป เช่น ARM หรือ LEG แล้วทดสอบว่า policy ย้ายแรงกระแทกไปยังอวัยวะที่ภารกิจถัดไปไม่ต้องใช้หรือไม่ ใช้ selective sacrifice index เปรียบเทียบ cue ARM กับ cue LEG และมี controls อย่างน้อยสามแบบ: ไม่มี cue, ปิด impairment และ cue สลับมั่ว ต้อง calibrate ก่อนว่าระดับ damage ของแขน/ขาทำให้อัตราความสำเร็จของภารกิจที่ใช้อวัยวะนั้นลดลงจริง

เกณฑ์ S3 ที่วางไว้คือ SSI เป็นบวกอย่างสม่ำเสมอทั้ง 3 seeds, สูงกว่า controls และยังรักษาอัตราสำเร็จของภารกิจถัดไปได้ดีขึ้นเมื่อมี cue งานนี้ยังอยู่นอกผลที่ผ่าน gate ในเอกสารฉบับนี้

## 6. Compute และคำขอ LANTA

จาก endpoint จริง: S1 ใช้ 17,203,200 transitions ต่อ seed และ S2 ใช้ 3,276,800 transitions ต่อ seed ที่ 16,384 transitions/update ตัวเลขการรัน S2 ที่ใช้เป็นหลักฐานใช้เวลา 4:11:18 ชั่วโมงบน WSL (`auto-loop/reports/jobs.md`)

สำหรับงานเต็ม วางแผน 56 training runs (S1 5, S2 24, S3 27), evaluation overhead 10%, S3 สมมติฐาน 800 updates หรือ 13,107,200 transitions ต่อ seed และ throughput LANTA 12,000 transitions/s ซึ่งยังไม่เคยวัดจริง ใช้ buffer 1.3 ค่า `node_hours` ใน M3 จึงเป็น 18:

`570,408,960 × 1.3 ÷ (12,000 × 3,600) = 17.17 node-hours`

จึงได้ **18 node-hours เป็น base estimate** และเสนอขอ **100 node-hours** สำหรับ benchmark, การแก้ recipe และการทำซ้ำ seed ที่ไม่ผ่าน ตัวเลข 18 ไม่ใช่การรับรองเวลาบน LANTA; ต้องวัดก่อน submit ด้วย `scripts/lanta/bench_throughput.sbatch` และยังห้ามตีความว่า S3 ผ่านแล้ว

รายละเอียดสูตรอยู่ใน `planning/LANTA_Compute_Estimate_TH.md` และ milestone ที่ใช้ตรวจคือ `auto-loop/milestones/m3_compute.json`
